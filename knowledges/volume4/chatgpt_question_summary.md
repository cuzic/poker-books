# ポーカー CFR ソルバーの精度が出ない件の相談

## 背景

書籍『ゼロから勝てるテキサスホールデム』の巻4 (ターン・リバー編) を執筆するため、自作 Rust CFR ソルバーの出力と GTO Wizard の公開値を照合して精度検証している。**フロップ初手 CBet 頻度** を 30 ボードで比較したところ誤差が大きい。改修を重ねても改善しないので、根本原因について意見がほしい。

## シナリオ

| 項目 | 値 |
| --- | --- |
| ゲーム | NLHE ヘッズアップ |
| スタック | 100BB |
| pot | 7BB (BTN 2.5x open → BB call) |
| effective_stack | 97BB |
| hero | BTN (IP) |
| villain | BB (OOP) |
| hero_range | BTN 100bb open (48%、~635 コンボ) |
| villain_range | BB defend vs BTN (54%、718 コンボ) |
| street | Flop 初手 |
| bet_sizes | [0.33, 0.5, 0.75, 1.0, 1.5] × pot |
| algorithm | External Sampling MCCFR (ES-MCCFR) + DCFR |

検証対象は「BTN がフロップで CBet する頻度 (= 1 - check 頻度)」。GTO Wizard 値を正として誤差を測る。

## 検証結果の推移

### ラウンド 1: デフォルト config

```
multistreet: false
max_raises: 1          (Bet + 1回レイズ、3bet なし)
max_iterations: None   (= タイムアウトまで)
realtime_timeout_secs: 5
```

結果: **平均絶対誤差 28.3%、最大 68%**

傾向:
- ドライボード (K72r, A72r) → 誤差 ±10% (合格)
- ペアボード (K44, A99) → +17〜33% (ソルバが過剰ベット)
- ウェット連結 (987ss, JT9ss) → +55〜58% (大きく過剰ベット)
- モノトーン (987mono, AKQmono) → +55〜68% (最悪)

**共通点**: ソルバが**すべてのボードで 75-90% ベット**に張り付く。ウェットボードで GTO Wizard が 20-35% に落とすのに、ソルバは下げられない。

### 改修 H1: villain レンジ拡張

BB defend range を 558 → 718 コンボに拡張 (連結ハンドを厚く)。同じ config で再走:

結果: **平均誤差 28.3% → 28.7% (ほぼ変化なし)**

| ボード | 参考 | 初回 | 拡張後 |
| --- | --- | --- | --- |
| K44 | 43 | 76 (+33) | 81 (+38) 悪化 |
| AKQmono | 15 | 70 (+55) | 89 (+74) 大悪化 |
| 987mono | 20 | 88 (+68) | 80 (+60) やや改善 |

レンジ拡張は効いていない。

### ラウンド 2: multistreet + 高めの iteration

```
multistreet: true          (ターン/リバーのチャンスノードを展開)
max_raises: 3              (3bet まで許容)
max_iterations: Some(5000)
realtime_timeout_secs: 120
```

結果 (スモーク 3 ボード):

| ボード | 参考 | default | v2 | actual_iter | time(s) |
| --- | --- | --- | --- | --- | --- |
| K72r | 91 | 88 (-3) | **71 (-20)** | 5000 | 4.7 |
| JT9ss | 25 | 83 (+58) | 76 (+51) | 5000 | 4.9 |
| 987mono | 20 | 80 (+60) | 82 (+62) | 5000 | 4.5 |

**所見**:

1. ドライボード (K72r) が 88 → 71 に下がりすぎ (参考は 91)
2. ウェット (JT9ss) は微改善のみ、モノトーン (987mono) はほぼ変わらず
3. 全ボードが `max_iterations: 5000` に到達で打ち切り (timeout 120s に到達せず)
4. 1 反復 ≈ 1ms (multistreet=true で 3 ストリート展開にしては非常に速い → ツリーが小さい疑い?)
5. `exploitability_bb` は未実装 (null) で収束判定できない

## 疑問

### Q1. multistreet 実装のバグ可能性

multistreet=true で K72r が下がる (91→71) のは「ターン/リバーで villain にエクイティが渡る」ことを織り込んだ挙動として理解できる。しかし同じ multistreet=true で JT9ss や 987mono が下がらない (76, 82 のまま) のは矛盾している。

**本来期待する挙動**:
- K72r (ドライ): 未来ストリート影響小 → CBet 高止まり (85-95%)
- 987mono (ウェット): 未来ストリート影響大 → CBet 低下 (15-25%)

現状は**逆**に見える (K72r だけ下がり、ウェットは動かない)。multistreet のツリー展開 or エクイティ伝播のバグ仮説を検証するにはどうしたらいいか？

### Q2. 5000 反復で MCCFR は収束するか

1 反復 1ms 程度。30 ボードで 2.5 分。ES-MCCFR で multistreet フロップサブゲームを収束させるために、通常何反復必要？ 50k?  500k?  どの範囲まで増やす価値があるか？

### Q3. レンジ vs レンジの初期戦略バイアス

MCCFR の初期戦略が uniform (全アクション等確率) だと、iteration 不足時に「全体が高頻度ベット」寄りに残る偏りはあり得るか？ Regret Matching の初期値が regret=0 → uniform policy → CFR 最初は全部同じ確率 → ただし bet サイズが 5 種なので bet 全体で 5/7 ≈ 71% に寄る可能性？ これが「ベット 75-90% 張り付き」の正体の可能性は？

### Q4. ショーダウン EV or エクイティ計算の疑い

レンジ対レンジのエクイティ計算で、モノトーン/連結ボードで hero 側エクイティが**過大**評価されていると、ソルバは「全ベットして勝てる」判定になる。PokerStove 等の独立計算値と照合すべきか？ よくある実装ミスはどこに潜むか？

### Q5. 他に疑うべき場所

この症状 (「ソルバがあらゆるボードで一方向 (全ベット) に張り付く」) を見たら、まずどこを疑う? 経験則を教えてほしい。

## 補足情報

- ベットサイズは 5 種 (0.33, 0.5, 0.75, 1.0, 1.5 × pot) を候補にしている
- ES-MCCFR + DCFR (Discounted CFR、α=1.5/β=0/γ=2 相当) を使用
- isomorphism reduction は有効 (スート正規化)
- ソルバは他のベンチマーク (verify_gto.py の簡単なプリフロップ局面) では妥当な挙動を見せている
